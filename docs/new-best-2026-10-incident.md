## 확정할 수 없는 원인

세 HTML 원본을 확보하지 못했으므로 **원본 응답에 해당 순위가 없었는지,
파서가 존재하는 항목을 놓쳤는지 실행별로 판별할 수 없다.**
상위 5개는 모두 성공하고 누락 순위가 달라지는 패턴은 일시적 원본 누락과 부합하지만
이를 입증하지 않는다. 빈 제목, DOM 중첩/변경 등 파서 누락도 가능하다.
10/14 원본 HTML에서 90위가 없었다는 내용은 사용자가 제공한 과거 분석이며,
이번 조사에서 해당 HTML을 다시 확인하거나 세 실패에 일반화하지 않았다.

확정된 복원력 문제는 완전하지 않은 HTTP 성공 응답을 한 번 파싱한 뒤 즉시 종료하고,
원본 자료를 1일만 보존해 사후 원인 구분을 할 수 없다는 점이다.

## 변경

- 완전성 검증 실패에 한해 최초 요청 + 최대 두 번 재요청, 간격 15초/45초.
  정상 응답이면 즉시 종료한다. 기존 45초 요청 timeout은 유지한다.
- 재요청은 동일 URL에 Cache-Control/Pragma no-cache를 보내 재검증을 요청한다.
  서버가 이를 준수하거나 재요청으로 복구된다는 보장은 없다.
- 매 응답을 독립적으로 파싱한다. 서로 다른 시도나 과거 데이터로 구멍을 메우지 않는다.
- 1~200위가 모두 있어야 저장한다. 한 소스 내 중복 순위도 실패 처리한다.
  최종 실패 시 latest/day/index에 쓰지 않고 exit 2를 유지한다.
- 전송 예외는 기존처럼 exit 1로 즉시 실패하며, 이미 확보한 시도 자료를 보존한다.
- 시도별 HTML/JSON 및 전체 시도 내역을 저장한다. 재시도로 성공한 경우도
  workflow artifact를 보존하며 보존 기간을 14일로 늘린다.
- `missingWithRankMarker`: 넓은 목록 DOM 탐색에서 `.num` 순위 표시는 있지만
  파싱 결과에는 없는 순위. 빈 제목/중첩 등 파서 처리 경로를 조사한다.
- `missingWithoutRankMarker`: 해당 목록 DOM 탐색에도 순위 표시가 없는 경우.
  원본 HTML을 검토해야 한다. 마크업 변경도 가능하므로 이 값만으로 서버 누락으로 단정하지 않는다.
- 공개 데이터 구조, 기존 수집 cron, publish 로직은 유지한다.

## 검증

`python -m unittest discover -s tests -v` 및 `npm test`.
새 회귀 테스트는 실제 장애 HTML이 아닌 명시적인 합성 fixture를 사용한다.
정상 200개, 92/183/90위 단일 누락, 103/115/151/156/191위 복수 누락,
지속 실패/재시도 성공, 시도 간 혼합 방지, 빈 제목/중첩 DOM/중복 순위,
마지막 성공 데이터 보존, 전송 실패, 진단 파일 정리, no-cache 요청을 검사한다.
모든 문피아 요청과 대기 시간은 mock 처리한다. PR CI도 오프라인 테스트만 실행한다.

실제 운영에서의 재시도 복구율은 병합 후 정기 수집의 진단 자료로 확인해야 한다.
